# 성능 감각

작은 데이터로 만들면 잘 돌아가다가, 실제 데이터에서 느려지는 일이 흔합니다.
이 프로젝트의 코드 리뷰에서 나온 지적 대부분이 이 유형이었습니다. 시뮬레이터에는 사진이 12장뿐이지만 실제 사진첩에는 수만 장이 있습니다.

## 질문 하나: "이게 1,000배가 되면?"

코드를 쓸 때 데이터가 많아지면 어떻게 될지 한 번씩 물어봅니다.

| 상황 | 12장일 때 | 수만 장일 때 |
| --- | --- | --- |
| 목록을 전부 한 번에 그리기 | 문제없음 | 화면이 멈춤 |
| 탭을 열 때마다 사진첩 전체 훑기 | 순간 | 몇 초 |
| 반복문 안에서 목록 검색 | 문제없음 | 수백만 번 |
| 장소마다 서버에 이름 묻기 | 3번 | 수백 번 → 차단 |

## 흔한 원인과 해법

### 1. 보이지 않는 것까지 만든다

화면에 10개만 보이는데 500개를 다 만드는 경우입니다.

- 해법: 보이는 것만 만들기(`LazyVStack`, `List`). 웹의 가상 스크롤.

### 2. 반복문 안의 검색 (숨은 O(n²))

```swift
for stop in stops {
    let index = stops.firstIndex(of: stop)     // 매번 처음부터 찾음
}
```

겉보기엔 반복문 하나지만, 안에서 또 전체를 훑으므로 n×n번입니다.

- 해법: 순번을 미리 알고 있으면 넘겨주기(`enumerated()`), 또는 딕셔너리로 한 번에 찾기.
- JS로 치면 `arr.find`를 반복문 안에서 쓰는 대신 `Map`을 만들어 두는 것.

### 3. 같은 일을 반복한다

- 탭을 누를 때마다 전체를 다시 읽기 → 한 번 읽고 **바뀌었을 때만** 다시 읽기
- 같은 좌표의 이름을 매번 서버에 묻기 → **캐시**(한 번 받은 답을 저장해 두기)

캐시를 쓰면 "언제 옛 답을 버릴지"(무효화)를 같이 정해야 합니다.

### 4. 화면 스레드에서 무거운 일

계산이 길어지면 그동안 화면이 멈춥니다.

- 해법: 백그라운드로 보내기. → [비동기와 스레드](04-async-and-threads.md)

### 5. 외부 서비스를 한꺼번에 많이 부른다

서버는 대개 횟수 제한이 있습니다.

- 해법: 필요한 것만(화면에 보이는 것만), 간격을 두고, 실패하면 나중에 다시.

### 6. 큰 이미지를 그대로 쓴다

1,200만 화소 사진 한 장은 메모리에서 약 48MB입니다. 썸네일 100개에 원본을 쓰면 앱이 종료됩니다.

- 해법: 표시할 크기만큼만 요청하기.

## 멈출 수 없는 긴 작업

긴 작업에는 세 가지가 필요합니다.

1. **진행 표시**: 얼마나 됐는지
2. **취소**: 중간에 그만둘 수 있게
3. **중간 저장**: 꺼져도 처음부터 다시 하지 않게

이 앱의 분석은 200장마다 저장하고 구간 사이에 취소를 확인합니다. 다만 구간 하나가 아주 길면(연속 촬영 1,500장) 그 안에서는 셋 다 안 됩니다. 작업을 나누는 단위가 너무 크면 생기는 문제입니다.

## 먼저 재고, 그다음 고친다

느릴 것 같다는 추측만으로 코드를 복잡하게 만들지 않습니다.

1. 실제 데이터로 돌려 본다.
2. 어디가 느린지 **잰다**(Xcode의 Instruments).
3. 가장 느린 곳부터 고친다.

다만 위의 여섯 가지처럼 "데이터가 늘면 반드시 문제가 되는" 구조는 미리 피하는 게 낫습니다.
