# 테스트

## 두 종류

| | 로직 테스트 (단위 테스트) | 화면 테스트 (UI 테스트) |
| --- | --- | --- |
| 무엇을 | 함수 하나의 입력 → 결과 | 앱을 실제로 띄워 버튼을 누름 |
| 웹으로 치면 | Jest / Vitest | Playwright / Cypress |
| 속도 | 74개에 0.5초 | 5개에 약 2분 |
| 잡는 것 | 계산·규칙 오류 | 화면 연결 오류, 흐름 오류 |
| 위치 | `PhotoTidyCore/Tests/` | `PhotoTidyUITests/` |

**빠른 테스트를 많이, 느린 테스트를 조금** 두는 게 기본입니다(테스트 피라미드).

## 로직 테스트의 모양

```swift
func testPhotoOutsideRadiusStartsNewStop() {
    // 준비: 약 1.1km 떨어진 사진 두 장
    let photos = [tp("a", at: 0, 37.0), tp("b", at: 60, 37.01)]
    // 실행
    let stops = TimelineBuilder.stops(photos, radius: 200)
    // 확인
    XCTAssertEqual(ids(stops), [["a"], ["b"]])
}
```

- **준비 → 실행 → 확인** 세 단계입니다.
- 함수 이름이 곧 "무엇을 보장하는지"입니다. 실패했을 때 이름만 봐도 무엇이 깨졌는지 알 수 있어야 합니다.

## 무엇을 테스트할까

1. **보통의 경우**: 가까운 사진 두 장은 한 곳.
2. **경계값**: 간격이 **정확히** 60초일 때는? 59초, 61초는? 버그는 `<`와 `<=`를 헷갈리는 경계에서 가장 많이 납니다.
3. **빈 입력**: 사진이 0장일 때 터지지 않는지.
4. **이상한 입력**: 위치 정보가 없는 사진, 깨진 저장 파일.

## 테스트를 테스트하기

테스트가 통과한다고 해서 쓸모 있는 테스트라는 뜻은 아닙니다. **무엇을 넣어도 통과하는 테스트**일 수 있습니다.

확인하는 법: 코드를 **일부러 망가뜨려 보고** 테스트가 실패하는지 봅니다(변이 테스트).

이 프로젝트에서 12가지를 망가뜨려 봤더니 11가지는 잡혔고, 하나는 통과해 버렸습니다.

```swift
// "이전 날" = 목록에서 오늘보다 앞선 날 중 마지막
days.last { $0 < day }
// 일부러 first로 바꿈 → 테스트가 그대로 통과!
```

원인은 테스트 데이터였습니다. 앞선 날이 **하나뿐인** 경우만 확인해서, `first`든 `last`든 같은 답이 나왔습니다. 앞선 날이 둘인 경우를 추가하니 잡혔습니다.

교훈: **테스트 데이터는 "틀린 구현과 맞는 구현이 다른 답을 내는" 것이어야 합니다.**

## 화면 테스트의 모양

```swift
app.tabBars.buttons["타임라인"].tap()
XCTAssertTrue(app.buttons["이전 날"].waitForExistence(timeout: 20))
```

- 버튼을 **이름**(접근성 라벨)으로 찾아 누릅니다.
- 화면이 뜰 때까지 **기다렸다가** 확인합니다. 기다리지 않으면 화면이 아직 안 떠서 실패합니다. 화면 테스트가 들쭉날쭉한 가장 흔한 이유입니다.

주의할 점:

- 이름을 바꾸면 테스트가 깨집니다. 화면을 고칠 때 이름은 유지해야 합니다.
- 테스트끼리 상태가 섞입니다. 이 프로젝트는 테스트 전에 앱을 지워 초기화합니다.
- 이 프로젝트의 정리 테스트는 **실제로 사진 1장을 지웁니다.** 시뮬레이터에서만 돌려야 합니다.

## 테스트가 못 잡는 것

모든 테스트가 통과해도 버그는 있을 수 있습니다. 테스트는 **적어 둔 상황만** 확인하기 때문입니다.

이 프로젝트의 테스트는 전부 통과하지만, 코드 리뷰에서 문제가 20건 가까이 나왔습니다. "나중에 받은 옛날 사진", "수백 곳짜리 앨범", "공유 중 날짜 변경"처럼 테스트가 다루지 않는 상황이었습니다.

그래서 테스트, 코드 리뷰, 실제 기기에서 써 보기를 **같이** 합니다. 서로 잡는 것이 다릅니다.

## 테스트하기 어려운 코드

- 사진첩, 지도, 네트워크처럼 **바깥에 의존하는 코드**는 테스트하기 어렵습니다.
- 그래서 그런 코드는 최대한 얇게 두고, 판단은 순수 함수로 뺍니다. → [프로젝트 구조](07-project-structure.md)
