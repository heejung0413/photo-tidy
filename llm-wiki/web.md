# 웹 타임라인

2026-11-17 추가. 설계는 `docs/superpowers/specs/2026-11-17-web-timeline-design.md`, 실행법은 `web/README.md`.

## 무엇인가

아이폰 앱의 타임라인 기능만 브라우저로 옮긴 정적 사이트(`web/`). 사진 파일을 올리면 지도·날짜별 머문 곳·공유 이미지를 만든다.
정리 기능은 없다(웹은 사진첩을 읽거나 지울 수 없다). 하루씩 넘겨 보기도 없고, 올린 사진 전체를 앨범 보기처럼 한 화면에 보여 준다.

## 기술

Vite + React + TypeScript, Leaflet + 오픈스트리트맵 타일, `exifr`(사진 정보), Nominatim(장소 이름), 일반 CSS, Vitest, Playwright(시스템 크롬).

## 정한 것

- 받아 온 이름은 머문 곳 id가 아니라 좌표 칸(`placeKey`)으로 기억한다. 사진을 더 올려 머문 곳이 다시 만들어져도 이름이 유지된다.
- 받아 온 이름과 직접 붙인 이름은 `localStorage`(`photo-tidy.place-names`, `photo-tidy.custom-place-names`)에 저장한다. 사진은 저장하지 않는다.
- 사진의 촬영 시각에는 시간대가 없어서, 보는 사람 브라우저의 시간대 시각으로 읽는다.
- 사진 정보를 읽지 못한 사진도 넣는다(위치 없음, 파일 수정 시각). 사진이 아닌 파일만 건너뛴다.
- 공유 이미지는 버튼을 누른 순간의 내용으로 만들고, 그림을 받는 사이 도착한 이름만 다시 채운다(아이폰과 같다).
- 지도는 Leaflet을 `useEffect`로 직접 쓴다(react-leaflet 없음). 창 크기가 바뀌면 범위를 다시 맞춘다.

## 코드 검토 (2026-11-17)

독립 검토자 1명에게 웹 코드 전체를 읽게 했다. 지적 10건 중 4건을 화면 테스트로 재현해 고쳤다.

| 문제 | 고친 방법 |
| --- | --- |
| 읽는 도중 "전부 지우기"를 누르면 읽던 사진이 되살아남 | 지울 때마다 올라가는 번호(`generation`)를 두고, 그 전에 읽기 시작한 묶음은 버린다 |
| 공유 이미지에 늦게 온 장소 이름이 안 들어감 | 버튼을 누른 때의 함수가 아니라, 부르는 순간의 값을 읽는 `latestName`을 쓴다 |
| 올리는 영역 밖에 떨어뜨리면 브라우저가 그 사진으로 이동해 타임라인이 사라짐 | 페이지 전체가 떨어뜨린 파일을 받는다(`App`의 window 리스너) |
| "읽지 못한 파일" 안내가 지워지지 않고 계속 쌓임 | 방금 올린 묶음의 수만 보여 준다 |

같이 고친 것: 묶음을 연달아 올리면 진행 표시가 섞이던 것(차례로 읽게 줄을 세움).
확인해 보니 문제가 아니었던 것: 이름 요청 간격(화면 테스트로 5번·1초 이상 간격 확인), 남반구·서반구 좌표 부호(시드니·뉴욕 샘플로 확인).

처음에 남겼던 5건도 같은 날 이어서 처리했다.

| 문제 | 처리 |
| --- | --- |
| 썸네일과 공유 이미지가 원본 사진을 그대로 불러 메모리를 많이 씀 | 사진을 올린 뒤 짧은 변 264px짜리 작은 그림을 하나씩 만들어 쓴다(`services/thumbnails.ts`). 원본 주소는 더 이상 화면에 올리지 않는다 |
| "이름 없음"과 "요청 실패"를 구분하지 않음 | 이름 서비스가 이름 없다고 답하면 `null`, 요청이 실패하면 오류를 던지게 나눴다. 이름 없는 곳은 그 방문 동안 다시 묻지 않고, 연달아 3번 실패하면 1분간 묻지 않는다(`PlaceNameLookup`의 `maxFailures`, `pauseAfterFailures`) |
| 사진 정보를 읽을 때 파일 전체를 메모리에 올림 | 브라우저에서는 파일을 그대로 넘겨 필요한 앞부분만 읽게 했다. 테스트(노드)에서만 통째로 읽는다 |
| 경도 180도 근처에서 머문 곳 중심 계산이 틀림 | 경도를 가까운 쪽으로 모아 평균 낸다(`meanLongitude`). **아이폰 앱(`TimelineBuilder`)도 같이 고쳤다** |
| 공유 이미지 테스트가 크기만 봄 | 저장한 PNG의 픽셀을 읽어 지도의 핀·선 색과 썸네일 색을 확인한다 |

아이폰 앱의 `PlaceNameLookup`은 그대로다(`nil`을 실패로 본다). 애플 지오코더는 이름 없음과 실패를 같은 오류로 주기 때문에 나누지 않았다.

남은 것: 썸네일을 만들 때 사진 한 장을 통째로 풀어야 하는 것은 그대로다(한 번에 한 장). 날짜변경선을 넘는 사진들의 **지도 범위 맞추기**(화면 지도, 공유 이미지)는 고치지 않았다.

## 두 번째 코드 검토 (2026-11-17, `/code-review high`)

지적 10건 중 "실제 버그일 가능성이 높다"고 본 5건을 사용자 요청으로 고쳤다. 다섯 건 모두 화면 테스트로 먼저 재현했다.

| 문제 | 고친 방법 |
| --- | --- |
| 묶음을 연달아 올리고 읽는 중에 지우면, 줄에서 기다리던 묶음이 올라옴(첫 검토 수정의 빈틈) | 묶음을 **올린 때**의 `generation`을 기억해, 줄에서 기다리던 묶음도 버린다 |
| 썸네일이 다 만들어지기 전에 저장하면 이미지에 회색 빈 칸 | 공유 이미지가 필요한 썸네일을 직접 만들어 받는다(`ensureThumbnail`) |
| 앞 묶음의 썸네일을 다 만들 때까지 다음 묶음을 읽지 않음 | 썸네일 만들기를 사진 읽기와 다른 줄(`thumbnailQueue`)로 분리 |
| 이름 요청이 연달아 실패해 쉰 뒤 다시 묻지 않음 | 답을 못 받은 곳(`PlaceNameLookup.isUnknown`)이 남으면 65초 뒤 다시 묻는다 |
| 좁은 화면에서 머문 곳을 눌러도 화면 밖의 지도만 움직임 | 지도가 화면 위로 밀려나 있으면 지도가 보이게 올려 보낸다 |

테스트 요령: 썸네일이 느린 상황은 `createImageBitmap`을 감싸 지연을 넣어 만들고, 1분 넘는 대기는 Playwright의 `page.clock`으로 시간을 넘긴다.

나머지 5건도 이어서 고쳤다.

| 문제 | 고친 방법 | 재현 |
| --- | --- | --- |
| **아이폰 앱**: 탭에 돌아올 때마다, 무관한 사진첩 변경마다 앨범 전체를 다시 읽고 화면을 새로 만듦 | 처음 열 때만 화면을 새로 만든다. 그 뒤(탭 복귀, 사진첩 변경 알림)에는 조용히 다시 읽어 머문 곳이 달라졌을 때만 고친다(`TimelineModel.refreshIfChanged`). 달라진 것이 없으면 로딩 표시도, 진행 중인 이름 받기도 건드리지 않는다 | 재현 테스트 없음. 기존 화면 테스트 7개로 "바뀌면 따라간다"만 확인 |
| 지도를 직접 확대한 뒤 창 크기가 바뀌면 전체 범위로 되돌아감 | 지도를 누르면(`pointerdown`) 다시 맞출 범위를 비운다. 건드리지 않은 지도는 계속 다시 맞춘다 | 화면 테스트 |
| 이름이 올 때마다 핀을 전부 다시 그려 말풍선이 닫힘 | 핀을 머문 곳 id로 기억해 두고, 이름만 바뀌면 글자만 고친다. 경로 선은 따로 그린다 | 화면 테스트 |
| 내려받기 주소를 1초 뒤에 풀어, 확인 창을 띄우는 브라우저에서 저장이 실패할 수 있음 | 60초 뒤에 푼다 | 화면 테스트(4초 뒤에도 주소가 살아 있는지). 아이폰 사파리에서 실제로 실패했는지는 미확인 |
| 페이지 안의 썸네일을 끌었다 놓으면 새 사진으로 올라갈 수 있음 | 썸네일을 끌 수 없게 하고(`draggable={false}`), 페이지 안에서 시작한 끌기는 받지 않는다 | 화면 테스트(가짜 끌기 이벤트). 실제 크롬에서 그렇게 올라갔는지는 미확인 |

## 사진을 많이 올릴 때 (2026-11-17)

사용자가 "이미지를 많이 하니까 안 된다"고 했다(어떤 화면이었는지는 듣지 못함). 재현해 본 것:

| 상황 | 결과 |
| --- | --- |
| 같은 아이폰 사진(2MB) 100·300·1,000장 | 정상. 목록 0.2~1초, 썸네일 4·11·39초, 메모리 17~29MB |
| 위치·날짜가 다른 사진 600장(머문 곳 180곳, 30일) | 정상. 썸네일까지 12.6초, 오류 없음 |
| **사진이 든 폴더를 통째로 떨어뜨림** | **안 됨.** "읽지 못한 파일 1개"만 나오고 아무것도 안 올라감 → 고침 |

고친 방법: 떨어뜨린 것이 폴더면 그 안의 파일을 폴더 속 폴더까지 꺼낸다(`core/droppedEntries.ts`의 `collectFiles`, `services/droppedFiles.ts`). 숨김 파일(`.DS_Store`)은 건너뛴다. 폴더 내용물은 한 번에 다 오지 않아 빈 목록이 올 때까지 읽어야 한다.
화면 테스트는 CDP `Input.dispatchDragEvent`에 폴더 경로를 넣어 실제 떨어뜨리기를 흉내 낸다.

폴더가 원인이 아니었을 수도 있다. 사용자가 본 증상을 확인해야 한다(실제 큰 HEIC, 실제 이름 서비스의 요청 제한, 공개 사이트 쪽 문제 등은 재현해 보지 못했다).

## 배포 (2026-11-17)

- 공개 주소: https://photo-tidy-timeline.vercel.app
- Vercel 계정 `heejung0413`의 개인 공간(`heejung0413's projects`), 프로젝트 `photo-tidy-timeline`. 같은 계정의 `Tix2U` 팀에는 올리지 않는다.

## 안 한 것, 모르는 것

- 실제 사진(수백 장, HEIC, 아이폰 브라우저에서 고른 사진)으로는 써 보지 않았다.
- 머문 곳이 많으면 이름이 다 뜨는 데 그만큼 초가 걸린다(1초에 하나).
